# Push SprintFlow to GitHub + deploy to SAPL VPS via CI/CD

- Goal — Publish `sprintflow-fullstack` as a new public GitHub repo with a CI/CD pipeline that builds, tests, and deploys it to the SAPL VPS on every push to `main`.
- Current context / assumptions —
  - Code lives at `/home/shridharsabat/sprintflow-intake/sprintflow-fullstack/`, branch `master`, NO git remote yet. Backend: FastAPI + SQLite (`backend/`, `requires-python >= 3.11`, uv-managed, serves port 8000). Frontend: React + Vite + TS (`frontend/`, `npm run build` = `tsc --noEmit && vite build`, API base = `VITE_API_URL || '/api'`, dev proxy `/api -> 127.0.0.1:8000`).
  - No `Dockerfile`, no `docker-compose.yml`, no `.github/` in the repo yet. `.gitignore` already excludes `node_modules/`, `.venv/`, `.env`, `*.db`, `dist/`.
  - `gh` CLI is authenticated as `shridhargsabat` (keyring). New repo will be `shridhargsabat/sprintflow`, public.
  - Proven in-house pattern (mirror it): ITMS repo (`~/itms`) uses `.github/workflows/ci-cd.yml` (pinned-action SHAs, GHCR images, SSH deploy with secrets `VPS_HOST` / `VPS_USER` / `VPS_SSH_KEY`, `scripts/build-deploy.sh`, compose `pull_policy: always`, smoke test). SprintFlow is simpler (SQLite volume instead of Postgres).
  - ASSUMPTIONS TO CONFIRM IN TASK 0: VPS reachable over SSH as `root` (same host as ITMS until proven otherwise); Docker Engine (not bare podman) with the compose plugin on the VPS; no custom domain yet (deploy on `http://VPS_HOST:<port>` first, DNS/HTTPS later).
- Architecture / proposed approach — Two GHCR images (`sprintflow-backend`, `sprintflow-frontend`) built on the VPS over SSH exactly like ITMS: frontend is an nginx image serving `dist/` and reverse-proxying `/api/` to the backend; backend persists `sprintflow.db` on a named volume. GitHub Actions runs frontend checks + backend pytest on PRs/pushes, then the SSH deploy job on `main`.

### Task 3 — Backend Dockerfile (5 min)
- New file `backend/Dockerfile` (exact content):
```dockerfile
FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app
RUN pip install --no-cache-dir uv
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev
COPY app.py db.py models.py auth.py ./
COPY routers/ ./routers/
RUN mkdir -p /data

EXPOSE 8000

Then `docker run --rm -e SPRINTFLOW_JWT_SECRET=dev-only -p 8000:8000 sprintflow-backend:local & sleep 6; curl -s http://127.0.0.1:8000/api/health` → expect `{"status":"ok","database":"sqlite"}`; kill the container after.

## Risks, tradeoffs, and open questions
- RISK: SQLite on a single volume = no horizontal scaling, and a volume delete loses everything. Accepted for v1 (matches current architecture); mitigation: add a nightly `sqlite3 .backup` cron on the VPS (follow-up task, not in this plan).
- RISK: JWT secret + Vite port defaults. `.env` on the VPS is the only secret store; dev default must never reach prod (compose `:?` guard fails fast if unset). Vite `port: 5173` is dev-only and irrelevant to the nginx image.
- TRADEOFF: building images ON the VPS over SSH (ITMS pattern) vs building in Actions runners. Kept the VPS build: zero runner minutes, identical environment, proven script. Downside: first deploy is slow (npm ci + uv sync on small VPS).
- TRADEOFF: `CORS allow_origins` includes `"*"` — harmless behind same-origin nginx (`/api` proxied, no cross-origin in prod) but should be tightened later; not blocking.
- OPEN: VPS_HOST/VPS_USER/VPS_SSH_KEY values — Task 0/8 need them (ask user or copy ITMS deploy target).
- OPEN: custom domain + HTTPS (e.g. `sprintflow.<domain>`) — plan ships plain HTTP on a port; TLS via VPS reverse proxy (Traefik/Caddy) is a follow-up.
- OPEN: branch protection on `main` (require checks before merge) — recommended after first green run; NOT enabled in this plan to avoid locking out the initial push.
